How the OSSPREY Chatbot Works

A question-answering assistant for the repository you have loaded

← Back to the User Registry

In one sentence

The chatbot is a thin wrapper over RepoWise. OSSPREY does not run its own language model or its own retrieval index — it forwards your question to the RepoWise service, which does the retrieval and the generation, and renders what comes back.

RepoWise is a separate service maintained alongside OSSPREY. It runs on the same host and is never exposed to the browser directly.

What the wrapper actually does

The browser only ever talks to OSSPREY's own /api/chat/* endpoints. A single backend module, app/repowise.py, is the one place that knows RepoWise's URL, payload shapes and quirks. It is responsible for:

  • Deriving the project id. A GitHub URL becomes owner-repo in lowercase, matching RepoWise's own parse_github_url() character for character. A mismatch here would silently answer questions about the wrong repository.
  • Keeping RepoWise off the public surface. Its address comes from REPOWISE_BASE_URL (default http://localhost:8000) and is never sent to the browser.
  • Turning failures into something readable. A refused connection or a timeout becomes "The assistant is temporarily unavailable", not a stack trace.
  • Staying stateless. Conversation state round-trips through the client, so no request depends on which worker served the previous turn.

The request flow

  1. Browser
  2. OSSPREY /api/chat/*
  3. adapter
  4. RepoWise
  5. retrieval + LLM
  6. answer

1. Opening a conversation

When you load a repository, the widget calls POST /api/chat/session with the repo's GitHub URL. The adapter asks RepoWise whether that project is already indexed. If it is, the call returns immediately. If it is not, RepoWise crawls and embeds the repository first — that can take minutes, which is why the widget shows a "preparing context" state rather than appearing to hang.

2. Asking a question

Each question is a POST /api/chat/message carrying the query, the project id and the conversation state from the previous turn. The adapter forwards it to RepoWise's /api/query with temperature: 0 and a five-result retrieval budget, then returns the answer along with the sources it was drawn from and any follow-up questions RepoWise suggests.

3. While you wait

Generation runs on CPU and is not fast, so the widget shows a rotating status word and a live elapsed timer instead of a frozen spinner, then reveals the finished answer progressively.

Endpoints

OSSPREY endpoint Calls on RepoWise Purpose
GET /api/chat/health GET /api/system-status Is the assistant up, and how many projects are indexed
POST /api/chat/session GET /api/projects/<id>, POST /api/projects/add Ensure the repository is indexed; return its project id
POST /api/chat/message POST /api/query Answer one question in the context of that repository

Limits worth knowing

  • GitHub repositories only. Apache and Eclipse foundation projects are selected by name and carry no GitHub URL, so there is nothing for RepoWise to index and the chatbot cannot answer questions about them.
  • The first question about a new repository is slow. Indexing happens on demand, once per repository.
  • Answers are grounded in the repository, not in OSSPREY's forecasts. The chatbot reads the repository's own content; it does not see the sustainability model's predictions.
  • If RepoWise is down, the chatbot is down. The rest of the dashboard is unaffected — the adapter fails on its own.
